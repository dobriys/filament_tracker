# Архитектура поддержки разных принтеров и систем мультиподачи

Статус: спецификация (2026-07-04). **Фаза A реализована** (capabilities + пресеты +
capability-рендер карточки для Klipper/Moonraker); B/C/D — впереди. Связано с
[SaaS-планом](../README.md) (транспортный шов — общий).

## Проблема

Сейчас приложение заточено под один принтер — **Anycubic Kobra S1 Combo** (ACE Pro:
сушилка + 4-слотовая мультиподача, прошивка Rinkhals с Moonraker/Happy-Hare). Всё
остальное — второй принтер (Kobra 3/X, Bambu Lab, Prusa), а тем более произвольный
принтер публичного пользователя — либо не поддержано, либо ломает вёрстку.

Нужно: подключать **разные принтеры**, автоматически показывать **правильный визуал**
под конкретное железо (с сушилкой/без, с мультиподачей/без, N слотов), и оставить
запас под облачный SaaS, где у людей будет что угодно.

## Что захардкожено сейчас

| Слой | Файл | Привязка |
|---|---|---|
| Модель | `backend/app/models/printer.py` | `integration_type = manual \| moonraker`. Ни бренда, ни модели, ни возможностей. Слоты — плоский `slot_index`. |
| Протокол | `backend/app/services/moonraker.py` | Klipper/Moonraker **+ Rinkhals**: `parse_hub` читает `mmu` (гейты ACE), `parse_dryer` — `mmu_machine`/`filament_hub` (сушилка ACE). |
| Клиент | `backend/app/api/printers.py::_moonraker_client()` | Прямой HTTP к Moonraker. |
| Визуал | `frontend/src/pages/Dashboard.jsx` | `MoonrakerCard` жёстко рисует «Слоты ACE» + `DryerControls`. Предполагает наличие ACE-хаба и сушилки. |

Итог: код неявно считает, что «принтер = Kobra S1 Combo».

## Принцип: строим от возможностей, а не от «базы моделей»

Соблазн — найти большую БД принтеров и рисовать по названию модели. Это ловушка:
- прошивки разные (Rinkhals / сток / моды) — модель не гарантирует поведение;
- у публичных пользователей будет что угодно;
- каноничной открытой БД принтеров+AMS с API не существует — её пришлось бы вести руками.

Поэтому разделяем **три независимых слоя**:

### Слой 1. Протокол (как разговариваем) — адаптеры интеграции

Абстракция `PrinterAdapter`: единый интерфейс независимо от железа.

```
class PrinterAdapter (Protocol):
    def test_connection() -> {ok, detail}
    def get_status() -> PrinterStatus        # нормализованный статус
    def get_capabilities() -> Capabilities   # что удалось определить из телеметрии
    def get_hub() -> list[Slot]              # слоты мультиподачи (пусто — нет MMU)
    def get_dryer() -> Dryer | None          # None — сушилки нет
    def list_history() / history_raw()       # задания для импорта/списания
    def get_totals() -> Totals | None
    # управление (опционально, по capability):
    def start_drying(...) / stop_drying(...)
```

Конкретные адаптеры:
- **`moonraker`** (есть, отрефакторить в адаптер) — Klipper-семейство: Anycubic на
  Rinkhals, Voron, самосборы. ACE/Happy-Hare — частный случай внутри.
- **`bambu`** (новый, большой) — MQTT/TLS + FTPS. Облако или LAN access code. AMS —
  своя модель. Отдельный крупный проект, см. ниже.
- **`prusalink` / `octoprint`** — по желанию позже.
- **`manual`** (есть) — без live-связи, только склад + gcode.

**Транспорт vs протокол — два разных шва.** Протокол = «как понимать данные принтера».
Транспорт = «как до принтера дотянуться»: `DirectHTTP` (self-host, есть) и
`RelayTransport` (SaaS через домашнего агента, из SaaS-плана). Адаптер ходит через
транспорт. Один рефактор `_moonraker_client()` закрывает и мультипринтерность, и облако.

### Слой 2. Возможности (что у принтера есть) — `capabilities`

JSON-поле на принтере, нормализованное. Драйвер всего визуала и логики.

```jsonc
{
  "tool_count": 4,          // экструдеров/тулов
  "has_mmu": true,          // система мультиподачи
  "mmu_slots": 4,           // число слотов (гейтов)
  "mmu_name": "ACE Pro",    // для лейблов/брендинга (необязательно)
  "has_dryer": true,        // активная сушилка
  "has_chamber": false,     // отапливаемая камера
  "has_heated_bed": true,
  "controls": ["dryer_start_stop"]  // что умеем не только читать, но и слать
}
```

Источник значений (по приоритету):
1. **автоопределение** из телеметрии (`get_capabilities()` адаптера) — самое честное;
2. **пресет** модели (см. слой 3) — префилл при заведении принтера;
3. **ручная правка** пользователем.

### Слой 3. Визуал — рендер по возможностям + пресеты для брендинга

Карточка принтера собирается **из секций по флагам `capabilities`**, а не по «это ACE»:
- нет `has_mmu` → нет блока слотов, только статус+прогресс+температуры;
- нет `has_dryer` → нет блока сушилки;
- `mmu_slots = N` → ровно N чипов слотов;
- лейблы обобщить: «Слоты ACE» → «Слоты мультиподачи» (или `mmu_name`, если задан).

Хорошая новость: `dryer` уже отдаётся данными и блок уже условный
(`Dashboard.jsx`), до полноценного capability-рендера недалеко.

## Пресеты принтеров (маленькая курируемая база)

Не 1000 моделей, а **курируемый список 10–20 популярных** — по образцу уже
существующего `backend/app/services/catalog_seed.py` (каталог филаментов).

Формат `printer_presets.py` (или JSON):
```python
PRESETS = [
  # brand, model, integration, capabilities, image
  ("Anycubic", "Kobra S1 Combo", "moonraker",
     {"tool_count": 4, "has_mmu": True, "mmu_slots": 4, "mmu_name": "ACE Pro",
      "has_dryer": True}, "anycubic-kobra-s1.svg"),
  ("Anycubic", "Kobra 3",        "moonraker",
     {"tool_count": 1, "has_mmu": True, "mmu_slots": 4, "has_dryer": False}, ...),
  ("Bambu Lab", "X1 Carbon + AMS", "bambu",
     {"tool_count": 1, "has_mmu": True, "mmu_slots": 4, "has_chamber": True}, ...),
  ("Prusa", "MK4 + MMU3",        "prusalink",
     {"tool_count": 1, "has_mmu": True, "mmu_slots": 5}, ...),
  ("Generic", "Klipper / Moonraker", "moonraker", {}, ...),  # авто
]
```

При заведении принтера: выбрал пресет → префилл `integration_type` + `capabilities`
+ число слотов + картинка-силуэт. Всё редактируемо. Пресеты расширяются PR-ами.

## Изменения модели данных

`Printer` (+ миграция Alembic):
```
brand: str | None            # "Anycubic"
model: str | None            # "Kobra S1 Combo"
capabilities: JSONB          # см. слой 2, default {}
# integration_type: расширить словарь: manual | moonraker | bambu | prusalink | octoprint
```
Слоты (`PrinterSlot`) уже generic — менять не нужно; число слотов задаётся при заведении
из `mmu_slots`.

Обратная совместимость: существующий принтер без `capabilities` → считаем «moonraker с
автоопределением», как сейчас. Миграция может проставить пресет Kobra S1 Combo для
текущего единственного принтера.

## Bambu Lab — почему это отдельный большой кусок

- **Не Moonraker.** Протокол — MQTT (телеметрия/команды) + FTPS (файлы/gcode).
- **Доступ:** облако (аккаунт Bambu + токен) ЛИБО LAN-режим (IP + access code + serial).
- **AMS:** своя модель — влажность, слоты, RFID-катушки, до 4× AMS. Маппинг на нашу
  `Slot`-модель нужно продумать.
- Есть готовые библиотеки (напр. `bambulabs_api`), но это полноценный второй адаптер
  с собственным жизненным циклом соединения. **Делать под реальный спрос**, не на старте.

## Роадмап по фазам

- **Фаза A — capability-driven (дёшево, сразу польза, без облака).**
  Модель (`brand/model/capabilities` + миграция) → `printer_presets.py` → рефактор
  `moonraker.py` в `MoonrakerAdapter` с `get_capabilities()` → карточка рендерит секции
  по флагам. После этого приложение честно работает с **любым Klipper/Moonraker-принтером**
  (с ACE и без, с сушилкой и без). Kobra выглядит как сейчас; Kobra X/Voron не ломаются.
  *~80% ценности мультипринтерности малой кровью.*
- **Фаза B — транспортный шов.** `DirectHTTP` / `RelayTransport`. Общая с SaaS-планом.
- **Фаза C — адаптер Bambu.** MQTT + AMS. Самый дорогой кусок, отдельно, под спрос.
- **Фаза D — брендинг-визуал.** Картинки/силуэты принтеров, лёгкие темы под бренд.

## Открытые вопросы / риски

- Автоопределение возможностей из Moonraker: по каким объектам? (`mmu`, `mmu_machine`,
  `filament_hub`, число экструдеров, `heater_generic chamber`). Нужна карта эвристик.
- Пресеты vs автоопределение при конфликте — кто главный (предлагаю: авто > пресет).
- Bambu: облако или только LAN на старте? Где хранить access code (в SaaS — на агенте).
- Картинки принтеров — лицензии/источник (рисовать свои силуэты, не тянуть чужие рендеры).
- Маппинг мультиподачи разных вендоров на единую `Slot`-модель (нумерация с 0/1, RFID).

## Рекомендация

Начать с **Фазы A** (capabilities + пресеты + capability-рендер карточки) на
Klipper/Moonraker-семействе. Не гнаться сразу за Bambu. Транспортный шов (Фаза B)
делать совместно с SaaS-планом, когда до него дойдёт.
